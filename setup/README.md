# setup/ — one VM per role, from Ubuntu cloud images + cloud-init

This turns the single-host `../docker-compose.yml` stack into a small fleet of
Ubuntu KVM guests, one per **role**, each running just its slice of the stack
via its own `compose.yaml`.

The role directories here mirror the repo's module layout: `roles/edge`
pairs with `../modules/bff` and `../modules/keycloak`, `roles/fsp` with
`../modules/fsp01`. The BFF `connections.json` is regenerated by `render.sh`
(not copied from `../modules/bff/config/`); the FSP model files are copied
from `roles/fsp/models/`, itself seeded from `../modules/fsp01/models/`. The
edge's Kea, BIND and Keycloak config lives in `roles/edge/config/`; its
realm file is seeded from `../modules/keycloak/`.

| role   | node(s)                     | containers             | notes                                                                 |
|--------|-----------------------------|------------------------|-----------------------------------------------------------------------|
| `edge` | `rti-edge`                  | `rti-bff`, `rti-hmi`, `keycloak` | also runs the fleet's **Kea** DHCP + DDNS, **BIND** for `rti-domain.tld` and **mDNS**; static IP `192.168.150.2` |
| `so`   | `rti-so`                    | `rti-so`, `dr-leds`    | DHCP reservation `.11`                                                |
| `fsp`  | `rti-fsp01`, `rti-fsp02`, … | `rti-fsp`, `dr-leds` (1 each per node) | templated; add machines by editing `nodes.env`        |

Key differences from the root compose stack:

* **No `cert-generator` service.** `render.sh` mints one CA + server/client
  cert on the host (containerised `cfssl`), with SANs covering every node name
  and its `.local` alias, and embeds them in each node's cloud-init.
* **Name resolution is mDNS.** Every node runs `avahi`; peers are addressed as
  `<hostname>.local`. `connections.json` and the cert SANs use those names.
  No `/etc/hosts` wiring.
* **DNS for `rti-domain.tld`, alongside mDNS.** BIND on `rti-edge` is the
  fleet's resolver (DHCP hands out `192.168.150.2`): it answers the
  `rti-domain.tld` zone and its reverse zone itself and forwards everything
  else to the libvirt router. Kea registers every lease there through DDNS,
  so each node is also `<hostname>.rti-domain.tld`; `keycloak.rti-domain.tld`
  is an alias for the edge. The cert SANs cover these names too. The `.tld`
  marks the domain as made up (`DNS_DOMAIN` in `roles.env`).
* **Addressing is DHCP** handed out by `rti-edge` (Kea DHCPv4), with a static
  reservation per named node keyed by a MAC derived from the node name. The
  libvirt network does NAT + DNS only (no DHCP of its own).
* **Keycloak runs on the edge** (`start-dev`, realm `iec61850-test`
  imported at start), HTTP on port 8080 and HTTPS on 8443 with the fleet's
  server certificate. Its issuer is `http://keycloak.rti-domain.tld:8080`.
* **Images ship as `docker save` tarballs**, copied into each disk and
  `docker load`ed on first boot. Nothing is pulled from a registry.
* Images built by the root Compose file are named
  `${RTI_IMAGE_REPO}/rti-<role>:${RTI_IMAGE_TAG}`, where `<role>` is `bff`,
  `hmi`, `so` or `fsp`. The default repository is
  `netbeheer-nederland/iec61850-websocket`; published images use
  `ghcr.io/netbeheer-nederland/iec61850-websocket`. The default tag is `latest`.
  `build-tarballs.sh` reads these names and automatically tags the images as
  `rti-<role>:latest` before saving them, matching the fleet's
  Compose files and existing tarball filenames.
* **Plugins** keep their own name: `${RTI_IMAGE_REPO}/dr-leds:${RTI_IMAGE_TAG}`
  is saved as `dr-leds:latest`. Every SO and FSP node runs its own `dr-leds`
  (the sample plugin, on `127.0.0.1:8099`) and connects to it through
  `PLUGINS` in its compose file. The IO plugin `dr-panel` needs a Pi's GPIO,
  I2C and SPI devices, so it runs only on the Pis.
* Containers use `network_mode: host`.

## Layout

```
setup/
  roles.env          # image, network, per-role sizing + tarball payload
  nodes.env          # the fleet: one line per VM
  download-images.sh # fetch + verify the Ubuntu cloud image
  build-base.sh      # -> images/base-rti.qcow2 (docker, avahi, Kea, BIND baked in)
  build-tarballs.sh  # docker save rti-* -> images/*.tar
  render.sh          # certs + templates -> build/<node>/{user-data,meta-data,spec,compose.yaml}
  make-disks.sh      # per node: expanded standalone qcow2 + copy-in + seed ISO
  pi-user-data.sh    # base Pi image -> images/<hostname>.img with rti login, hostname (+ --role on first boot)
  launch.sh          # define libvirt net; virt-install edge first, then the rest
  destroy.sh         # virsh destroy/undefine the fleet
  up.sh              # render (+certs) -> make-disks -> launch
  base/rti-issue*    # console login banner baked into the base image
  libvirt/rti-demo-net.xml
  certs/             # cfssl config (ca/server/client CSR + profiles); shared with ../docker-compose.yml
  roles/<role>/{compose.yaml[.tmpl], cloud-init.yaml.tmpl}   # self-contained
  roles/edge/config/ # Kea DHCPv4 + DDNS, BIND options/zones (*.tmpl), keycloak/ realm
  roles/fsp/models/  # *.py copied to every fsp node (seeded from ../modules/fsp01/models/)
  images/  build/    # generated, git-ignored
```

## Host prerequisites

### Downloading and building base images on Ubuntu

On Ubuntu 24.04, install the tools used by `download-images.sh` and
`build-base.sh`:

```bash
sudo apt update
sudo apt install qemu-utils libguestfs-tools curl ca-certificates xz-utils
```

`qemu-utils` provides `qemu-img`, `libguestfs-tools` provides
`virt-customize`, and `xz-utils` provides `xz` for decompressing Pi images.
The build also requires:

* An x86-64 host for the default amd64 VM image. Raspberry Pi images
  (`--rpi 3`, `--rpi 4` or `--rpi 5`) build natively with libguestfs on an
  ARM64 host, or on an x86-64 host through `qemu-user-static` emulation
  and `sudo` (see [Raspberry Pi base images](#raspberry-pi-3-4-and-5-base-images)).
* Internet access and working DNS for package installation inside the image.
* Writable space in `setup/images/`; allow roughly 10–15 GB for downloading
  and building one target, with additional space for each retained image.
* The source image downloaded first with `./download-images.sh`, using the
  same `--rpi` argument as the build when selecting a Raspberry Pi model.

Host Docker, an SSH public key and the libvirt fleet tools are required for
later setup stages; they are not prerequisites for `build-base.sh` itself.

Ubuntu can install `/boot/vmlinuz-*` with permissions that prevent your user
from reading them. Libguestfs needs a readable host kernel to build its
temporary appliance. If supermin fails with
`cp: cannot open '/boot/vmlinuz-…' for reading: Permission denied`, apply
the [libguestfs Ubuntu workaround](https://libguestfs.org/guestfs-faq.1.html)
and rerun the build as your normal user:

```bash
sudo chmod 0644 /boot/vmlinuz*
./build-base.sh               # or ./build-base.sh --rpi 3|4|5
```

This makes the host kernel images readable; it does not change the guest
image's permissions. You may need to repeat it after a host kernel update.
`build-base.sh` checks for unreadable host kernels before replacing its output.

### Full VM fleet workflow

`qemu-kvm`, `libvirt` + `virtinst`, `libguestfs-tools` (`virt-customize`,
`virt-resize`, `guestfish`),
`cloud-image-utils` (`cloud-localds`) or `genisoimage`, `docker`, `curl`,
`gettext-base` (`envsubst`). An SSH public key at `~/.ssh/id_ed25519.pub`
(or `id_rsa.pub`), or `export SSH_PUBKEY=...` with the key itself, a `.pub`
file path, or a file name under `~/.ssh`.

## Run

```bash
cd setup

# one-time
./download-images.sh          # Ubuntu 24.04 cloud image
./build-base.sh               # golden image (needs network; a few minutes)
../scripts/build-rti-demo.sh --platform linux/amd64 bff hmi so fsp dr-leds   # amd64 images from upstream
docker pull quay.io/keycloak/keycloak:26.0       # Keycloak for the edge
./build-tarballs.sh           # automatically retag + docker save them

# each time you change nodes.env / templates
./render.sh                   # 1. mint certs (from certs/) + expand templates -> build/<node>/
./make-disks.sh               # 2. per-node expanded qcow2 + seed ISO
./launch.sh                   # 3. define libvirt net + virt-install (edge first)
# ...or just ./up.sh to run all three

virsh list --all
virsh console rti-edge        # watch first boot
ssh rti@192.168.150.2 'sudo cloud-init status --wait && docker ps'
```

`build-rti-demo.sh` clones the upstream `iec61850-websocket` repository
(branch `initial-refactor`), builds each image with `docker buildx` and
loads it into the host's Docker as
`netbeheer-nederland/iec61850-websocket/rti-<role>:latest` (plugins as
`.../dr-leds:latest` and `.../dr-panel:latest`), the names
`build-tarballs.sh` reads by default. Without image names it builds all of
them, including `dr-panel`, which the VMs don't use. Without `--platform` it
builds the arm64 Pi images instead, which do not run on the amd64 VMs. It also saves
`.tar.gz` archives for `deploy-rti-demo.sh` under `dist/rti-images-amd64/`;
the VM fleet does not use them.

To export images from another repository or tag, select them explicitly:

```bash
RTI_IMAGE_REPO=ghcr.io/netbeheer-nederland/iec61850-websocket \
RTI_IMAGE_TAG=latest ./build-tarballs.sh
```

The images published on GHCR are arm64 only, however, so they do not run
on the amd64 VMs.

The exporter requires all six source images (the four `rti-*` images,
`dr-leds` and Keycloak, `KEYCLOAK_IMAGE` to override) locally and does not pull them.
When using a custom repository or tag, set the same variables for every
`build-tarballs.sh` run.

`render.sh` is where the fleet's TLS material is generated: on the first run
(and whenever the node list — hence the SAN set — changes) it runs
containerised `cfssl` against the CSR/profile config in `certs/` and writes
`build/certs/{ca,server,client}*.pem`, which the templates then embed in each
node's cloud-init. There is no separate cert step. Host-side `certs/generate.sh`
remains available if you prefer to mint them with a local `cfssl`.

### Raspberry Pi 3, 4 and 5 base images

Select a model with the same argument when downloading and building:

```bash
./download-images.sh --rpi 3
./build-base.sh --rpi 3        # images/base-rti-rpi3.img
./download-images.sh --rpi 4
./build-base.sh --rpi 4        # images/base-rti-rpi4.img
./download-images.sh --rpi 5
./build-base.sh --rpi 5        # images/base-rti-rpi5.img
```

All three use Ubuntu's shared preinstalled ARM64 Raspberry Pi server image;
the downloader resolves the current 24.04 point release from `SHA256SUMS`
and verifies the compressed download. Building also needs `xz`. The output
is a standalone raw disk image, including Pi boot firmware, suitable for
flashing to an SD card or USB disk. Pi 3 means the 64-bit-capable 3B/3B+.

How the image is customised depends on the host:

* **ARM64 host:** `virt-customize` runs the package install natively, as for
  the VM image.
* **x86-64 host:** the script loop-mounts the image with `sudo`, chroots
  into it and lets the kernel run ARM64 binaries through qemu-user. Install
  the emulator and the partitioning tools once:

  ```bash
  sudo apt install qemu-user-static parted e2fsprogs
  ```

  The script checks that `qemu-aarch64` is registered with binfmt_misc
  (with the `F` flag) before it starts. Emulation is slow: expect 20 minutes
  or more for the upgrade and Docker install. The image's root partition
  is grown by 2 GB first (`RPI_IMAGE_GROW=…` to change), and cloud-init
  still expands it to the full card on first boot. If the build is
  interrupted, the script unmounts the image and detaches the loop device.

On both paths `flash-kernel` is rerun after the upgrade, so any newer
kernel and initrd are copied to the boot partition.

These commands bake the base OS and packages. The boot partition still has
Ubuntu's stock cloud-init, whose only user is `ubuntu`, with password SSH
login disabled, so make an image with a login for each Pi:

```bash
./pi-user-data.sh --rpi 5 --hostname rti-pi5   # images/base-rti-rpi5.img -> images/rti-pi5.img
```

This copies the base image to `images/<hostname>.img` (or `--out FILE`) and
writes `user-data` into the copy, creating `rti` (sudo, docker, i2c) with
`SSH_PUBKEY` and the hostname, without root (needs `mtools`). The base image
is never changed, so one `build-base.sh` serves every Pi; rerunning for the
same hostname replaces its image. Each copy takes the base image's size on
disk (about 4 GB). Add `--role` to have the Pi start its role on first boot
too (see the next section). For a card that is already flashed, mount its
`system-boot` partition and pass `--boot-dir <mountpoint>` instead; that
writes in place, and also changes the meta-data instance id so cloud-init
applies it on the next boot. The Pi takes its address by DHCP on `eth0`; it then answers as
`<hostname>.local`.

Provide ARM64 container images before deployment.
`make-disks.sh`, `launch.sh` and `up.sh` remain the KVM VM workflow; they do
not provision or boot physical Raspberry Pis. Without arguments, downloading
and building still produce the original amd64 VM base.

### Writing an image to an SD card or SSD

Flash the per-Pi `images/<hostname>.img` made by `pi-user-data.sh`, never
`build/<node>/seed.iso`. The seed
ISO is a ~400 KB data image holding only cloud-init's `user-data` and
`meta-data`, with no operating system. `launch.sh` attaches it to a VM as a
virtual CD-ROM next to the node's real disk (`build/<node>/<node>.qcow2`),
and cloud-init reads it at first boot. It is an ISO 9660 filesystem with no
partition table, so balenaEtcher warns that it does not look bootable. If
you write it anyway, the card or SSD holds only those two files and its
previous contents are gone.

For a Raspberry Pi, with Pi 5 as the example:

```bash
./download-images.sh --rpi 5
./build-base.sh --rpi 5                          # images/base-rti-rpi5.img
../scripts/build-rti-demo.sh                     # arm64 base + plugin images
./pi-user-data.sh --rpi 5 --hostname rti-fsp-pi5 \
  --role fsp --cp cp1 --model ../modules/fsp01/models/model_1.py
                                                 # -> images/rti-fsp-pi5.img
```

Then write `images/rti-fsp-pi5.img` with balenaEtcher (or `dd`). This
image has a partition table and the Pi boot firmware, so Etcher accepts it.

With `--role so` or `--role fsp`, the Pi starts its role on first boot;
`--cp`, `--port` and `--model` are the fsp settings, as for
`deploy-rti-demo.sh`. The role's files, about 170 MB of image archives (its
base image plus `dr-panel` and `dr-leds`) plus its compose file, `.env` and
model, are put in `rti/` on the boot partition
(512 MB, a few hundred MB free). On first boot cloud-init copies them to
`~rti/rti`, the directory `deploy-rti-demo.sh` uses, runs
`load-and-start.sh` there and deletes `rti/` from the boot partition. Follow
it in `/var/log/rti-first-deploy.log` on the Pi; the containers are up once
`docker ps` lists them.

Without `--role` the Pi gets only the login and hostname. Push the role
later from a workstation with `../scripts/deploy-rti-demo.sh` (see the
[repository README](../README.md)); that is also how to update a Pi that
already runs its role. Both use `../scripts/stage-rti-role.sh` to put the
role's files together.

An x86 PC that boots from the SSD has no workflow here yet: the scripts
only produce VM disks plus a separate seed ISO.

### Console login banner

Every base image (VM and Pi) shows the node's current configuration above the
console login prompt: hostname and `.local` name, IPv4 addresses, gateway,
the Compose project with its `PORT`/`CP`/`MODELPATH`, whether Kea DHCPv4,
Kea DDNS and BIND (`named`) are running (edge only) and each container's
state and health. It is
`/etc/issue.d/50-rti.issue`, regenerated every 30 seconds by
`rti-issue.timer` from `base/rti-issue`. agetty redraws the prompt only when
the text changes, and the banner is gone once you log in. Run
`sudo rti-issue` to refresh it immediately.

Tear down with `./destroy.sh` (add `--keep-network` to leave `rti-demo-net`).

## Connecting to a node with SSH

Every node, VM or Pi, has one login: `rti` (`VM_USER` in `roles.env`),
with passwordless `sudo` and membership of `docker`. Login is by key only:
cloud-init installs the `SSH_PUBKEY` found by `render.sh` (or
`pi-user-data.sh`) and locks the password, so use the matching private key.
Because the password is locked, `virsh console` shows the boot log and the
login banner but cannot log you in.

### Creating a key when you have none

`render.sh` and `pi-user-data.sh` stop with `no SSH_PUBKEY` when neither
`~/.ssh/id_ed25519.pub` nor `~/.ssh/id_rsa.pub` exists and `SSH_PUBKEY` is
unset. Create a key first. Either make it your default key, which the
scripts and `ssh` then pick up by themselves:

```bash
ssh-keygen -t ed25519 -C "rti-demo"    # accept ~/.ssh/id_ed25519
```

or create a separate key for the demo fleet and point the scripts at it:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/rti-demo -C "rti-demo"
export SSH_PUBKEY=rti-demo.pub         # a file name under ~/.ssh, a path, or the key itself
./up.sh                                # or ./render.sh && ./make-disks.sh && ./launch.sh
```

`ssh-keygen` asks for a passphrase. Press Enter twice for none, or set one
and load the key once per session with `ssh-add ~/.ssh/rti-demo`.

The key is written into the nodes at first boot, so nodes that already
exist keep their old key. Rebuild them after creating or changing it:
`./destroy.sh` and then `./up.sh` for the VMs. For a Pi, rerun
`./pi-user-data.sh` with the new `SSH_PUBKEY` and flash the new image, or
use `--boot-dir` for a card that is already flashed, and boot it again.

A separate key is not offered by default, so name it when connecting:

```bash
ssh -i ~/.ssh/rti-demo rti@192.168.150.21
```

or add `IdentityFile ~/.ssh/rti-demo` to the `~/.ssh/config` entry below.

From the host, address a VM by the IP in `nodes.env`; the host sits on
`virbr-rti` as `192.168.150.1`:

| node        | address          |
|-------------|------------------|
| `rti-edge`  | `192.168.150.2`  |
| `rti-so`    | `192.168.150.11` |
| `rti-fsp01` | `192.168.150.21` |
| `rti-fsp02` | `192.168.150.22` |

```bash
ssh rti@192.168.150.21                 # rti-fsp01
ssh rti@192.168.150.21 docker ps       # run a single command
```

The `<hostname>.local` names work too if the host resolves mDNS (Ubuntu
desktop does, through `avahi-daemon` and `libnss-mdns`); Pis are reached
this way, or by the address their DHCP server gave them:

```bash
ssh rti@rti-fsp01.local
ssh rti@rti-pi5.local                  # the --hostname given to pi-user-data.sh
```

To use the `rti-domain.tld` names from the host, send that domain to the
edge's BIND (systemd-resolved; lasts until `virbr-rti` goes down):

```bash
sudo resolvectl dns virbr-rti 192.168.150.2
sudo resolvectl domain virbr-rti '~rti-domain.tld'
ssh rti@rti-fsp01.rti-domain.tld
```

The same setting lets a browser on the host open Keycloak at
<http://keycloak.rti-domain.tld:8080> (`admin` / `admin`).

Each rebuild with `./up.sh` gives a node new SSH host keys, so `ssh`
refuses to connect with `REMOTE HOST IDENTIFICATION HAS CHANGED`. Drop the
old key and connect again:

```bash
ssh-keygen -R 192.168.150.21
ssh-keygen -R rti-fsp01.local
```

Or skip host-key bookkeeping for the throwaway fleet with an entry in
`~/.ssh/config`, after which `ssh rti-fsp01` is enough:

```
Host rti-edge rti-so rti-fsp*
    HostName %h.local
    User rti
    # only for a separate key:
    IdentityFile ~/.ssh/rti-demo
    StrictHostKeyChecking no
    UserKnownHostsFile /dev/null
    LogLevel ERROR
```

Use `HostName 192.168.150.21` and so on, one `Host` block per node,
if the host does not resolve `.local`.

Once logged in, each node runs its slice of the stack from
`/etc/rti/compose.yaml`. The containers are `rti-bff`, `rti-hmi` and
`keycloak` on the edge, `rti-so` and `dr-leds` on the SO, and on an FSP
`dr-leds` and one named after the node:

```bash
docker ps
docker logs -f rti-fsp01
docker compose -f /etc/rti/compose.yaml restart
sudo cloud-init status --wait          # first boot finished?
```

On the edge, check DHCP and DNS:

```bash
systemctl status kea-dhcp4-server kea-dhcp-ddns-server named
journalctl -u kea-dhcp4-server -f      # leases being handed out
dig +short rti-fsp01.rti-domain.tld    # registered by DDNS
dig +short -x 192.168.150.21
```

## Adding an FSP machine

Append a line to `nodes.env`:

```
"rti-fsp03  fsp   192.168.150.23   cp=cp3 port=5001 model=model3.py"
```

Drop `model3.py` in `roles/fsp/models/` (the canonical copy lives in
`../modules/fsp01/models/`), then `./up.sh`. `render.sh` picks up the new
node for the cert SANs, the Kea reservations and `connections.json`
automatically, and Kea adds it to `rti-domain.tld` when it takes its lease.

## Notes / limitations

* `launch.sh` boots `rti-edge` and waits for it to answer ICMP before starting
  the others, so Kea is live when they request a lease.
* The base image now carries Kea and BIND instead of `isc-dhcp-server`;
  rebuild it with `./build-base.sh` before the first `./up.sh` with this
  version. The services are disabled in the image and enabled by the edge's
  cloud-init only.
* A Pi written with `pi-user-data.sh --role` starts its role only on its
  first boot. If that fails, `rti/` stays on the boot partition; check
  `/var/log/rti-first-deploy.log`, then run `sudo /usr/local/sbin/rti-first-deploy`
  or deploy with `../scripts/deploy-rti-demo.sh`. The first-boot path has
  been tested on a scratch image, not yet on Pi hardware.
* The DDNS TSIG key is generated once into `build/edge/ddns-tsig.secret`
  and reused by later renders; delete it to get a new one.
* BFF service discovery is disabled (`RTI_DOCKER_ENABLED=false`) — it can't see
  other hosts' Docker. It uses the static `connections.json` only.
* `roles.env` and `libvirt/rti-demo-net.xml` both hard-code the
  `192.168.150.0/24` range; keep them in sync if you change it.
* `make-disks.sh` expands the root partition and filesystem to the configured
  role disk size before copying container tarballs. Each node has a standalone
  disk, so allow host disk space for each copy of the base OS and payload.
  If copying still runs out of space, increase that role's disk size in
  `roles.env`, then rerun `render.sh` and `make-disks.sh` with the fleet stopped.
  Provision enough guest space for both the tarballs and Docker's loaded images.
