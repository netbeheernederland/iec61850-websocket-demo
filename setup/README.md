# setup/ — one VM per role, from Ubuntu cloud images + cloud-init

This turns the single-host `../docker-compose.yml` stack into a small fleet of
Ubuntu KVM guests, one per **role**, each running just its slice of the stack
via its own `compose.yaml`.

The role directories here mirror the repo's module layout: `roles/edge`
pairs with `../modules/bff`, `roles/fsp` with `../modules/fsp01`. The BFF
`connections.json` is regenerated by `render.sh` (not copied from
`../modules/bff/config/`); the FSP model files are copied from
`roles/fsp/models/`, itself seeded from `../modules/fsp01/models/`.

| role   | node(s)                     | containers             | notes                                                                 |
|--------|-----------------------------|------------------------|-----------------------------------------------------------------------|
| `edge` | `rti-edge`                  | `rti-bff`, `rti-hmi`   | also runs the fleet's **dhcpd** + **mDNS**; static IP `192.168.150.2` |
| `so`   | `rti-so`                    | `rti-so`               | DHCP reservation `.11`                                                |
| `fsp`  | `rti-fsp01`, `rti-fsp02`, … | `rti-fsp` (1 per node) | templated; add machines by editing `nodes.env`                        |

Key differences from the root compose stack:

* **No `cert-generator` service.** `render.sh` mints one CA + server/client
  cert on the host (containerised `cfssl`), with SANs covering every node name
  and its `.local` alias, and embeds them in each node's cloud-init.
* **Name resolution is mDNS.** Every node runs `avahi`; peers are addressed as
  `<hostname>.local`. `connections.json` and the cert SANs use those names.
  No `/etc/hosts` wiring.
* **Addressing is DHCP** handed out by `rti-edge` (ISC `dhcpd`), with a static
  reservation per named node keyed by a MAC derived from the node name. The
  libvirt network does NAT + DNS only (no DHCP of its own).
* **Images ship as `docker save` tarballs**, copied into each disk and
  `docker load`ed on first boot. Nothing is pulled from a registry.
* Images built by the root Compose file are named
  `${RTI_IMAGE_REPO}/rti-<role>:${RTI_IMAGE_TAG}`, where `<role>` is `bff`,
  `hmi`, `so` or `fsp`. The default repository is
  `netbeheer-nederland/iec61850-websocket`; published images use
  `ghcr.io/netbeheer-nederland/iec61850-websocket`. The default tag is `latest`.
  `build-tarballs.sh` reads these names and automatically tags the images as
  `rti-<role>:latest` before saving them, matching the fleet's
  Compose files and existing tarball filenames.
* Containers use `network_mode: host`.

## Layout

```
setup/
  roles.env          # image, network, per-role sizing + tarball payload
  nodes.env          # the fleet: one line per VM
  download-images.sh # fetch + verify the Ubuntu cloud image
  build-base.sh      # -> images/base-rti.qcow2 (docker, avahi, dhcpd baked in)
  build-tarballs.sh  # docker save rti-* -> images/*.tar
  render.sh          # certs + templates -> build/<node>/{user-data,meta-data,spec,compose.yaml}
  make-disks.sh      # per node: expanded standalone qcow2 + copy-in + seed ISO
  launch.sh          # define libvirt net; virt-install edge first, then the rest
  destroy.sh         # virsh destroy/undefine the fleet
  up.sh              # render (+certs) -> make-disks -> launch
  libvirt/rti-demo-net.xml
  certs/             # cfssl config (ca/server/client CSR + profiles); shared with ../docker-compose.yml
  roles/<role>/{compose.yaml[.tmpl], cloud-init.yaml.tmpl}   # self-contained
  roles/fsp/models/  # *.py copied to every fsp node (seeded from ../modules/fsp01/models/)
  images/  build/    # generated, git-ignored
```

## Host prerequisites

### Downloading and building base images on Ubuntu

On Ubuntu 24.04, install the tools used by `download-images.sh` and
`build-base.sh`:

```bash
sudo apt update
sudo apt install qemu-utils libguestfs-tools curl ca-certificates xz-utils
```

`qemu-utils` provides `qemu-img`, `libguestfs-tools` provides
`virt-customize`, and `xz-utils` provides `xz` for decompressing Pi images.
The build also requires:

* An x86-64 host for the default amd64 VM image. Raspberry Pi images
  (`--rpi 3`, `--rpi 4` or `--rpi 5`) build natively with libguestfs on an
  ARM64 host, or on an x86-64 host through `qemu-user-static` emulation
  and `sudo` (see [Raspberry Pi base images](#raspberry-pi-3-4-and-5-base-images)).
* Internet access and working DNS for package installation inside the image.
* Writable space in `setup/images/`; allow roughly 10–15 GB for downloading
  and building one target, with additional space for each retained image.
* The source image downloaded first with `./download-images.sh`, using the
  same `--rpi` argument as the build when selecting a Raspberry Pi model.

Host Docker, an SSH public key and the libvirt fleet tools are required for
later setup stages; they are not prerequisites for `build-base.sh` itself.

Ubuntu can install `/boot/vmlinuz-*` with permissions that prevent your user
from reading them. Libguestfs needs a readable host kernel to build its
temporary appliance. If supermin fails with
`cp: cannot open '/boot/vmlinuz-…' for reading: Permission denied`, apply
the [libguestfs Ubuntu workaround](https://libguestfs.org/guestfs-faq.1.html)
and rerun the build as your normal user:

```bash
sudo chmod 0644 /boot/vmlinuz*
./build-base.sh               # or ./build-base.sh --rpi 3|4|5
```

This makes the host kernel images readable; it does not change the guest
image's permissions. You may need to repeat it after a host kernel update.
`build-base.sh` checks for unreadable host kernels before replacing its output.

### Full VM fleet workflow

`qemu-kvm`, `libvirt` + `virtinst`, `libguestfs-tools` (`virt-customize`,
`virt-resize`, `guestfish`),
`cloud-image-utils` (`cloud-localds`) or `genisoimage`, `docker`, `curl`,
`gettext-base` (`envsubst`). An SSH public key at `~/.ssh/id_ed25519.pub`
(or `id_rsa.pub`, or `export SSH_PUBKEY=...`).

## Run

```bash
cd setup

# one-time
./download-images.sh          # Ubuntu 24.04 cloud image
./build-base.sh               # golden image (needs network; a few minutes)
docker compose -f ../docker-compose.yml build    # build repository-named images
./build-tarballs.sh           # automatically retag + docker save them

# each time you change nodes.env / templates
./render.sh                   # 1. mint certs (from certs/) + expand templates -> build/<node>/
./make-disks.sh               # 2. per-node expanded qcow2 + seed ISO
./launch.sh                   # 3. define libvirt net + virt-install (edge first)
# ...or just ./up.sh to run all three

virsh list --all
virsh console rti-edge        # watch first boot
ssh rti@192.168.150.2 'sudo cloud-init status --wait && docker ps'
```

To export published images already pulled onto the host, select their
repository and tag explicitly:

```bash
RTI_IMAGE_REPO=ghcr.io/netbeheer-nederland/iec61850-websocket \
RTI_IMAGE_TAG=latest ./build-tarballs.sh
```

The exporter requires all four source images locally and does not pull them.
Set the same environment variables for Compose builds and tarball exports
when using a custom repository or tag.

`render.sh` is where the fleet's TLS material is generated: on the first run
(and whenever the node list — hence the SAN set — changes) it runs
containerised `cfssl` against the CSR/profile config in `certs/` and writes
`build/certs/{ca,server,client}*.pem`, which the templates then embed in each
node's cloud-init. There is no separate cert step. Host-side `certs/generate.sh`
remains available if you prefer to mint them with a local `cfssl`.

### Raspberry Pi 3, 4 and 5 base images

Select a model with the same argument when downloading and building:

```bash
./download-images.sh --rpi 3
./build-base.sh --rpi 3        # images/base-rti-rpi3.img
./download-images.sh --rpi 4
./build-base.sh --rpi 4        # images/base-rti-rpi4.img
./download-images.sh --rpi 5
./build-base.sh --rpi 5        # images/base-rti-rpi5.img
```

All three use Ubuntu's shared preinstalled ARM64 Raspberry Pi server image;
the downloader resolves the current 24.04 point release from `SHA256SUMS`
and verifies the compressed download. Building also needs `xz`. The output
is a standalone raw disk image, including Pi boot firmware, suitable for
flashing to an SD card or USB disk. Pi 3 means the 64-bit-capable 3B/3B+.

How the image is customised depends on the host:

* **ARM64 host:** `virt-customize` runs the package install natively, as for
  the VM image.
* **x86-64 host:** the script loop-mounts the image with `sudo`, chroots
  into it and lets the kernel run ARM64 binaries through qemu-user. Install
  the emulator and the partitioning tools once:

  ```bash
  sudo apt install qemu-user-static parted e2fsprogs
  ```

  The script checks that `qemu-aarch64` is registered with binfmt_misc
  (with the `F` flag) before it starts. Emulation is slow: expect 20 minutes
  or more for the upgrade and Docker install. The image's root partition
  is grown by 2 GB first (`RPI_IMAGE_GROW=…` to change), and cloud-init
  still expands it to the full card on first boot. If the build is
  interrupted, the script unmounts the image and detaches the loop device.

On both paths `flash-kernel` is rerun after the upgrade, so any newer
kernel and initrd are copied to the boot partition.

These commands bake the base OS and packages. Configure each Pi's cloud-init
on its boot partition and provide ARM64 container images before deployment.
`make-disks.sh`, `launch.sh` and `up.sh` remain the KVM VM workflow; they do
not provision or boot physical Raspberry Pis. Without arguments, downloading
and building still produce the original amd64 VM base.

Tear down with `./destroy.sh` (add `--keep-network` to leave `rti-demo-net`).

## Adding an FSP machine

Append a line to `nodes.env`:

```
"rti-fsp03  fsp   192.168.150.23   cp=cp3 port=5001 model=model3.py"
```

Drop `model3.py` in `roles/fsp/models/` (the canonical copy lives in
`../modules/fsp01/models/`), then `./up.sh`. `render.sh` picks up the new
node for the cert SANs, the `dhcpd` reservations and `connections.json`
automatically.

## Notes / limitations

* `launch.sh` boots `rti-edge` and waits for it to answer ICMP before starting
  the others, so `dhcpd` is live when they request a lease.
* BFF service discovery is disabled (`RTI_DOCKER_ENABLED=false`) — it can't see
  other hosts' Docker. It uses the static `connections.json` only.
* `roles.env` and `libvirt/rti-demo-net.xml` both hard-code the
  `192.168.150.0/24` range; keep them in sync if you change it.
* `make-disks.sh` expands the root partition and filesystem to the configured
  role disk size before copying container tarballs. Each node has a standalone
  disk, so allow host disk space for each copy of the base OS and payload.
  If copying still runs out of space, increase that role's disk size in
  `roles.env`, then rerun `render.sh` and `make-disks.sh` with the fleet stopped.
  Provision enough guest space for both the tarballs and Docker's loaded images.
