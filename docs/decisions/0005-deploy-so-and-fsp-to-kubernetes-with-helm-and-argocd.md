# Deploy the SO and FSP to Kubernetes with per-role Helm charts and ArgoCD ApplicationSets

## Context and Problem Statement

[ADR 0002](0002-maintain-both-a-docker-compose-and-a-vm-fleet-deployment-target.md)
keeps two deployment targets: the single-host `docker-compose.yml` and the
per-role fleet of VMs and Pis (`setup/`, `scripts/deploy-rti-demo.sh`). In
both, each SO and FSP is a hand-copied compose service or a line in
`setup/nodes.env`, and changes are pushed to machines with `scp` and `ssh`.
The demo has to grow to more SOs and FSPs, possibly at more than one site,
and the images are now published to the GitHub Container Registry
(`docs/docker-images-github.md`). How should the SO and FSP be deployed on
a Kubernetes cluster (k3s on the Pis), so that any number of installations
can run side by side and be added, changed and removed reproducibly?

## Decision Drivers

* **Growing number of SO and FSP installations per demo.** The scaling spec
  (`../specs/2026-09-20-compose-node-scaling-design.md`) targets
  tens of nodes. Every installation differs in control point, port, model and
  hardware, and today each one is configured by copying a block or a line.
* **Manual, push-based rollout to the Pis.** `deploy-rti-demo.sh` copies
  archives and compose files over `ssh` to each host. What runs on a Pi is
  known only by logging in, and a host that was missed or changed by hand
  silently drifts from what the repository describes.
* **Hardware-bound IO server next to the SO and FSP.** The IO server needs
  privileged access to the GPIO, I2C and SPI devices of one specific Pi and
  must run beside the SO or FSP it serves. Any orchestration must place both
  on the same node and never start a second copy that competes for the
  devices.
* **Images available from a registry since 2026-10.** The arm64 images can
  now be pulled from `ghcr.io/netbeheernederland/iec61850-websocket`, which
  removes the need to ship archives for machines that can reach the
  registry. A Kubernetes cluster pulls images rather than loading tarballs.

## Considered Options

* Per-role Helm charts (`rti-so`, `rti-fsp`), one release per installation,
  generated by ArgoCD ApplicationSets from one directory per installation
* One umbrella Helm chart per site, listing all its SOs and FSPs in values
* Plain manifests with a Kustomize overlay per installation, synced by ArgoCD
* No Kubernetes: keep the compose and VM/Pi targets of ADR 0002 only

## Decision Outcome

Chosen option: "Per-role Helm charts, one release per installation,
generated by ArgoCD ApplicationSets from one directory per installation",
because it is the only option that addresses both the growing number of
installations and the manual push-based rollout at once: an installation is
a directory with an `installation.yaml` (destination cluster and namespace)
and a `values.yaml` (control point, port, model, IO), the ApplicationSets in
`deploy/argocd/apps/` turn every directory into an Application, and ArgoCD
keeps each cluster equal to Git with automated sync, prune and self-heal.
Unlike the umbrella chart, installations are independent releases, so one
can live in another namespace or cluster and be changed or removed without
touching the others. Unlike Kustomize, per-installation settings are a few
values instead of patches against full manifests. The hardware driver is met
inside the charts: the IO server is an optional sidecar in the same pod, the
Deployment has one replica with the `Recreate` strategy, and the images are
pulled from GHCR with an image pull secret.

The decision adds a third deployment target. It does not change ADR 0002's
two targets, nor [ADR 0003](0003-ship-vm-fleet-images-as-docker-save-tarballs.md):
the VM fleet still ships tarballs, while this target requires the cluster to
reach the registry.

### Consequences

* Good, because adding, changing or removing an SO or FSP is a commit: a new
  directory under `deploy/installations/<role>/` creates the Application, and
  deleting it deletes the resources (ApplicationSet finalizer).
* Good, because what runs is visible and reverted to Git by ArgoCD
  (self-heal), instead of being known only per host.
* Good, because installations can be spread over namespaces and clusters,
  for example one cluster per site, by `destination` in `installation.yaml`.
* Good, because the IO server always lands on the same node as its SO or FSP
  and never runs twice for one installation (one replica, `Recreate`).
* Good, because the charts can be used without ArgoCD (`helm upgrade
  --install` with the same release name and values file).
* Bad, because the demo now has three deployment targets to keep consistent
  (compose, VM/Pi fleet, Kubernetes): an environment variable, port or
  health check change has to be made in each.
* Bad, because the FSP models now exist in three copies (`modules/fsp0*/`,
  `setup/roles/fsp/models/`, `deploy/helm/rti-fsp/models/`), since Helm cannot
  read files outside the chart.
* Bad, because the cluster needs registry access and secrets that are not in
  Git: an ArgoCD deploy key for the GitLab repository and a `ghcr-pull`
  secret per namespace, created by hand as of 2026-10-16.
* Bad, because with the image tag `latest` (the example values as of
  2026-10-16) ArgoCD sees no change when a new image is pushed; rollouts are
  only controlled when installations pin `sha-<commit>` tags.
* Bad, because the BFF's `modules/bff/config/connections.json` is still
  maintained by hand and must list the Service addresses of the Kubernetes
  installations.

### Confirmation

* On 2026-10-16, `helm lint` passed for both charts, and `helm template`
  with each example installation (`so/demo`, `fsp/cp1`, `fsp/cp2`), using the
  release names ArgoCD gives, produced the expected Deployments, Services and
  model ConfigMaps; the bundled models rendered byte for byte. The manifests
  have not yet been applied to a cluster, and the ArgoCD resources have only
  been checked as YAML.
* The decision is confirmed when `deploy/argocd/bootstrap.yaml` has been
  applied to the k3s cluster and the three example Applications are
  `Synced` and `Healthy`, with the SO and FSPs answering on `/api/status` and
  the IO sidecar driving the Pi's hardware.
* After-action review one month after that first deployment: compare the
  effort of adding an installation and rolling out an image with the
  `deploy-rti-demo.sh` flow, and check how often the three targets drifted.

## Pros and Cons of the Options

### Per-role Helm charts with ArgoCD ApplicationSets

`deploy/helm/rti-so`, `deploy/helm/rti-fsp`; `deploy/argocd/apps/rti-so.yaml`
and `rti-fsp.yaml` use the Git files generator on
`deploy/installations/<role>/*/installation.yaml`; see
`docs/kubernetes-argocd.md`.

* Good, because each installation is a small values file, which suits tens
  of installations.
* Good, because installations are independent releases with their own
  destination, so they scale across namespaces and clusters.
* Good, because ArgoCD replaces the `scp`/`ssh` rollout with pull-based,
  self-healing sync.
* Neutral, because it depends on ArgoCD's ApplicationSet controller, which is
  part of standard ArgoCD installations.
* Bad, because the Git files generator and relative value file paths add
  ArgoCD-specific indirection that a reader has to learn.

### One umbrella Helm chart per site

One release per site whose values list every SO and FSP, rendered in a loop.

* Good, because one file shows the whole site.
* Bad, because all installations of a site share one release and one
  destination: a change to one FSP re-renders and re-syncs the whole site,
  and installations cannot be spread over clusters.
* Bad, because a mistake in one entry fails the whole release, and therefore
  the whole site's rollout.

### Plain manifests with a Kustomize overlay per installation

A base Deployment and Service per role, and an overlay per installation.

* Good, because ArgoCD supports Kustomize natively and no templating
  language is needed.
* Bad, because per-installation settings (port in the container, probes and
  Service; model ConfigMap; optional IO sidecar) need several patches each,
  which grows with the number of installations.
* Bad, because optional parts such as the IO sidecar need extra components
  or overlays instead of one value.

### No Kubernetes: compose and VM/Pi targets only

Keep ADR 0002's targets and the scripts.

* Good, because there is nothing new to learn or operate.
* Bad, because adding an installation stays a copy-and-edit task and the
  rollout stays manual and push-based, so neither driver is addressed.

* Implementation: `deploy/helm/`, `deploy/argocd/`, `deploy/installations/`;
  usage in `docs/kubernetes-argocd.md`; images in
  `docs/docker-images-github.md`.
* Follow-up decisions this one makes necessary or possible:
  * how secrets (GHCR pull secret, mTLS certificates for `certs.secretName`)
    get into the cluster, e.g. Sealed Secrets or External Secrets, instead of
    by hand;
  * how image tags are promoted to installations (pinned `sha-<commit>`
    tags, possibly updated by ArgoCD Image Updater);
  * a single source for the FSP models instead of three copies;
  * generating the BFF's `connections.json` from the installation
    directories, as `setup/render.sh` does for the VM fleet;
  * whether Kubernetes later replaces one of ADR 0002's targets, which would
    supersede ADR 0002.
